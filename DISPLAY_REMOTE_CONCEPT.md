# Display & Remote Control — Concept

A pattern for driving a fullscreen presentation display (laptop) from a
separate mobile remote, with the two devices talking directly over the
local WiFi network. There's no fixed set of scenes — each presentation
defines its own.

---

## The Core Idea

Two devices — a **laptop running the presentation** and a **mobile phone
acting as the remote** — sit on the same WiFi network and stay in sync
through a live WebSocket connection. The laptop hosts the connection and
is the single source of truth, holding state in memory.

```
┌─────────────────────┐   WebSocket    ┌───────────────────────────┐
│   Mobile             │   (LAN, WiFi)  │   Laptop                  │
│  (Remote)            │◄──────────────►│   (Presentation Display)  │
│                      │                │   — also runs the WS      │
│  [button press]  ──► │───── send ────►│     server + holds state  │
│                      │◄──── ack  ─────│   in memory               │
└─────────────────────┘                └───────────────────────────┘
```

The laptop never takes input from the remote's UI directly — it only
reacts to messages on the socket. The phone never shows the
presentation itself. All coordination flows through the one open
socket. State lives only in the laptop's process memory — nothing is
persisted, which is fine, since a laptop restart mid-event just resets
to `welcome` (or the presentation's defined start scene) when it comes
back up.

Both the **scene types available** and **which buttons the remote
shows** are not fixed — they're defined per presentation (see
"Per-Presentation Config" below), so a different talk/event can ship a
completely different set of slides/scenes and a completely different
remote layout without touching this core sync mechanism.

---

## The State Object

State is a `scene` discriminated union plus a timestamp.

```ts
type DisplayScene =
  | { type: "welcome" }
  | { type: "closing" }
  | { type: "poll-live" }
  | { type: "concept-carousel"; control?: "play" | "pause" | "next" | "prev" | "stop" }
  | { type: "demo-loading" }
  | { type: "answer-reveal"; count: number; total: number }      // e.g. correct answers so far / total
  | { type: "recap"; primary: number; secondary: number; rate: number }  // e.g. topics, questions, completion %
  | { type: "message"; text: string; sub?: string }
  | { type: "concept-card"; concept: { ... }; related: [...]; index: number; total: number }; // e.g. "Pull Request" + related terms

type DisplayState = {
  scene: DisplayScene;
  updatedAt: number;   // epoch ms — used to de-dupe renders
};
```

The `DisplayScene` union above is just **one example set**. A given
presentation defines its own scene types from scratch, or reuses/
extends this list — see below.

## Per-Presentation Config

Since a presentation's slide/scene count and content differ every time,
neither the laptop nor the phone should hardcode "these N scenes, these
buttons." Instead, each presentation ships a small **config file**
(JSON, checked into the presentation's own folder, or picked from a
dropdown when the laptop app starts):

```json
{
  "presentation": "GitHub Fundamentals — Session 1",
  "startScene": { "type": "welcome" },
  "buttons": [
    { "label": "Welcome",  "scene": { "type": "welcome" } },
    { "label": "Concepts", "scene": { "type": "concept-carousel" } },
    { "label": "Demo",     "scene": { "type": "demo-loading" } },
    { "label": "Poll",     "scene": { "type": "poll-live" } },
    { "label": "Recap",    "scene": { "type": "recap" } },
    { "label": "Closing",  "scene": { "type": "closing" } }
  ]
}
```

- The laptop loads this config on startup (or on switching
  presentations) and keeps it in memory alongside `DisplayState`.
- On connect, the laptop sends the **config first**, then the current
  state — the phone uses the config to know what buttons to render at
  all, before it needs to know what's currently showing.
- The remote's button panel is generated by mapping over
  `config.buttons` — nothing is hardcoded on the phone side, so a new
  presentation with 4 scenes and one with 12 both "just work" against
  the same remote app.
- Switching presentations mid-session (new talk, new config) is just
  the laptop loading a different config and re-broadcasting it — every
  connected remote's button list updates live.

The scene table above is one example config, not the only option.

## How State is Shared

### Why the laptop hosts the server

Something has to hold state and own the connection. The laptop is the
natural pick: it's the device running the presentation itself,
guaranteed to be open for the whole talk, and sitting on the same WiFi
as the phone. It runs a small embedded WebSocket server alongside the
presentation app (e.g. a `ws`/`socket.io` server started in the same
Electron/Node/local-dev process that renders the slides).

The phone is just a client. It connects out to the laptop's local IP —
no server of its own needed, and nothing to install beyond opening a
page in its browser.

### Connecting — phone joins the laptop's socket

```
ws://<laptop-local-ip>:<port>/display
```

- Both devices need to be on the same WiFi network (or the laptop can
  run its own mobile hotspot and the phone joins that — works
  identically, and is the more reliable option in venues with flaky/
  locked-down conference WiFi).
- On page load, the phone either has the IP saved (last-used, from
  `localStorage`) or the laptop shows a **pairing screen**: its local
  IP, port, and a QR code encoding the `ws://` URL, so you scan it with
  the phone's camera instead of typing an IP address.
- The phone connects directly; the laptop's WS server accepts the
  connection and immediately sends the **config, then the current
  state**, so there's no blank screen and no "what buttons do I even
  have" moment.
- If the WiFi drops or the laptop app restarts, the phone auto-reconnects
  with backoff (3 s) and re-syncs config + state on reconnect.
- More than one phone can connect to the same laptop if needed — the
  server just broadcasts state to every connected client, though for a
  single presenter this is normally exactly one remote.

### Writing state — a message over the open socket

```json
// remote → display
{ "type": "set-scene", "scene": { "type": "concept-carousel", "control": "play" } }

// display → remote (ack)
{ "type": "ack", "updatedAt": 1234568000 }
```

The laptop applies the scene in memory, re-renders, and pushes the same
message back out to any other connected remotes so everyone's status
indicator stays in sync.

### What this gets you

- No servers or endpoints beyond the one embedded WS server the laptop
  runs for the duration of the talk.
- No dependency on internet connectivity at all — this works in a venue
  with no external network, as long as both devices share WiFi (or a
  plain mobile hotspot from one of the devices).
- The display renders purely off the `scene.type` payload it receives.
  "No blank screen" on connect, reconnect-with-backoff, and a keepalive
  ping to stop idle sockets from being dropped by routers all ride the
  same WebSocket.

## The Scenes — example set for a "GitHub Fundamentals" talk

| Scene | What the display shows |
|---|---|
| `welcome` | Title screen — "GitHub Fundamentals", session number, cover art |
| `closing` | End-of-session thank-you + teaser for the next session |
| `poll-live` | Live count of audience poll responses (e.g. "who's used Git before?") |
| `concept-carousel` | Auto-advancing slides through core terms — repo, commit, branch, pull request, issue |
| `demo-loading` | "Switching to live demo" holding screen before you share your terminal/browser |
| `answer-reveal` | Animated count-up as quiz responses come in (e.g. correct answers so far) |
| `recap` | End-of-session stats: topics covered, questions asked, quiz completion rate |
| `concept-card` | Full card for one term (e.g. "Pull Request") with its definition + related terms |
| `message` | Freeform text — e.g. a live Q&A prompt or a "grab this link" callout |

This is one possible config's scene set, not a fixed list — a different
presentation can use 3 of these, all 9, or add new `type`s the laptop
knows how to render. Scenes still share a key so that logically
continuous transitions (e.g. `demo-loading` → `answer-reveal`) don't
trigger a crossfade.

---

## Scene Transitions

The display wraps every scene in a `SceneTransition` component that
keeps the previous scene mounted underneath and fades/slides the new
one in on top, keyed by `sceneKey`.

```
outgoing  ─── fade-out + slide-up ──► unmounted after 750 ms
incoming  ─── fade-in  + slide-up ──► becomes new current
```

## The Remote Control

Panels of buttons plus a status indicator. The button set is not
hardcoded on the phone — it renders from whatever `config.buttons` the
laptop sent on connect (see "Per-Presentation Config"), so the layout
changes automatically per presentation instead of needing a remote-side
code change each time.

### Panels

**Scenes panel** — one button per entry in `config.buttons`, rendered
in the order the config lists them. Tapping a button sends a
`set-scene` message with that button's `scene` payload over the socket.
Add/remove/rename a scene in the config → the panel changes, no app
update needed.

**Carousel controls** — for any config button whose scene `type` is
`concept-carousel` (or any type the presentation marks as
"carousel-like"), the remote also shows Play / Pause / Next / Prev /
Stop transport buttons that send that scene with a `control` field. A
`seq` value is included so repeated identical commands (e.g. tapping
"Next" twice) are each treated as distinct events by the laptop.

**Concept card** — Prev / Show / Next selector; "Show" sends a
`concept-card` scene with the concept + related payload embedded in the
socket message. Only rendered if the current config includes a
`concept-card`-type scene.

**Session lifecycle** — a panel showing where the presentation is in
its own flow (e.g. Draft → Live → Wrapping up). This is just another
socket message the laptop keeps in its own in-memory session state;
whether it's worth having at all is a per-presentation call.

**Message** — two text inputs (main + optional sub-text) that send a
`message` scene over the socket. Shown whenever the config includes a
`message`-type entry.

### Status indicator

```
● connecting…     (amber)  — socket handshake in progress
● ready           (grey)   — connected, no command sent yet
● sending…        (amber)  — awaiting ack
● <last-scene>    (green)  — last command acknowledged
● offline         (red)    — socket dropped, retrying
```

"sending…" resolves on socket `ack`. "offline" is worth surfacing
clearly since there's no fallback API to retry against — reconnect is
the only path back.

## File & Project Structure

Splitting scenes and remote panels into their own files (instead of one
big component) is what makes the config-driven approach above actually
manageable day to day — a new scene is a new file, not a bigger switch
statement to scroll through.

### Display side

```
/display
  /scenes
    WelcomeScene.tsx
    ClosingScene.tsx
    ConceptCarouselScene.tsx
    DemoLoadingScene.tsx
    AnswerRevealScene.tsx
    RecapScene.tsx
    ConceptCardScene.tsx
    MessageScene.tsx
  DisplayMain.tsx
```

- Each file under `scenes/` is one scene, self-contained — its own
  layout, animation, and any scene-specific logic (e.g. the carousel's
  auto-advance timer lives inside `ConceptCarouselScene.tsx`, not in
  `DisplayMain.tsx`).
- `DisplayMain.tsx` is the **only** file that: opens the WS server,
  owns `DisplayState`, and maps `scene.type` → the matching scene
  component inside `SceneTransition`. It doesn't know *how* any scene
  renders, only which component to mount.
- Adding a scene = add one file to `scenes/`, add one line to
  `DisplayMain.tsx`'s type→component map, add one entry to a
  presentation's config. Nothing else changes.

### Remote side

```
/remote
  /panels
    ScenesPanel.tsx
    CarouselControls.tsx
    ConceptCardPanel.tsx
    MessagePanel.tsx
  /data
    configs/
      sample-event.ts        ← scenes + buttons for one presentation
    layouts/
      default-layout.ts      ← which panels show, in what order/grid
  RemoteMain.tsx
```

- Panels are presentational only — each one takes props (its slice of
  the config, a `send()` callback) and renders buttons. A panel never
  talks to the socket directly.
- `RemoteMain.tsx` is the only file that owns the WS client connection,
  receives `{ config, state }` from the laptop, and decides what to
  render — by walking the **layout** file and mounting the panel each
  entry names, wired up with the matching slice of the **scenes**
  config.
- Splitting **scenes config** from **layout config** is what makes the
  remote's layout independently customizable: the same button/scene
  config can be rendered as a single-column list on one event and a
  2×2 grid with the carousel controls pinned to the bottom on another,
  just by pointing `RemoteMain.tsx` at a different layout file — no
  change to which scenes exist or what they're called.

```ts
// data/layouts/default-layout.ts — shape, illustrative
export const layout = [
  { panel: "ScenesPanel",      area: "top" },
  { panel: "CarouselControls", area: "middle", showIf: "concept-carousel" },
  { panel: "ConceptCardPanel", area: "middle", showIf: "concept-card" },
  { panel: "MessagePanel",     area: "bottom" },
];
```

- `RemoteMain.tsx` filters this list by `showIf` against the currently
  loaded scenes config (a panel with no matching scene type in the
  current presentation just isn't rendered), then renders whatever's
  left in `area` order. A different presentation can ship its own
  layout file the same way it ships its own scenes config.

## Auth & Security

With no backend session or cookie, the local-network flavor of auth is
lightweight:

- The WS server only listens on the local network interface (not
  0.0.0.0 to the internet) — anyone off the WiFi can't reach it at all.
- A short shared **pairing PIN**, generated fresh each time the display
  starts and shown on the pairing screen, is required in the WebSocket
  handshake. The remote enters it once (or scans it via the QR code,
  which can encode PIN + IP together) and it's cached for reconnects.
- This trades an authenticated admin session for "you had to be able to
  see the display's screen to get the PIN" — appropriate for a single
  event on a controlled venue WiFi, not for anything exposed publicly.

## Summary

```
Mobile (remote, same WiFi as laptop)
  RemoteMain.tsx                    ← owns the WS client
    │  connect → ws://<laptop-ip>:<port>
    │  ◄── receives { config, state } on connect
    │  renders panels/*.tsx per data/layouts/*.ts
    │  send { set-scene, scene }
    ▼
Laptop (presentation display)
  DisplayMain.tsx                   ← owns the WS server + DisplayState
    │  loads a presentation's scenes config
    │  broadcasts config + state to all connected remotes
    │  maps scene.type → the right scenes/*.tsx component
    ▼
  <SceneTransition sceneKey={scene.type}>
    {scene.type === "welcome" && <WelcomeScene />}
    {scene.type === "concept-card" && <ConceptCardScene ... />}
    {/* one line per scenes/*.tsx file */}
  </SceneTransition>
```

One WebSocket connection, laptop ↔ phone, direct over WiFi. One
in-memory state object, owned by `DisplayMain.tsx`. Scenes and remote
panels each live in their own file; which scenes exist and how the
remote lays out its panels are both just data (`configs/` and
`layouts/`), swappable per presentation without touching component
code.
